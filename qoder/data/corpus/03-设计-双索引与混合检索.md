# 设计：ngram 全文 + HNSW 向量双索引

## 为什么是两条通道

只用全文索引，遇到「同义改写」就失效：资料里写的是「近似最近邻」，用户搜的是「ANN 向量检索」，词面对不上。只用向量索引，遇到专有名词、参数名、错误码又容易漂：`efSearch`、`OB_ERR_…` 这类 token 在向量空间里区分度不高。

所以两条通道都保留：**全文索引保证「词对得上就一定找得到」，向量索引负责「换个说法也能靠近」**，最后用 RRF（Reciprocal Rank Fusion）把两个有序列表融合。

## 表结构

片段表是核心，同一张表上建两个索引：

```sql
CREATE TABLE zx_chunks (
  id BIGINT NOT NULL AUTO_INCREMENT,
  document_id BIGINT NOT NULL,
  seq INT NOT NULL,
  heading VARCHAR(255) NOT NULL,
  body TEXT NOT NULL,
  char_start INT NOT NULL,
  char_end INT NOT NULL,
  start_line INT NOT NULL,
  end_line INT NOT NULL,
  embedding VECTOR(384) NOT NULL,
  PRIMARY KEY (id),
  KEY ix_doc_seq (document_id, seq),
  FULLTEXT KEY ft_body (body) WITH PARSER ngram,
  VECTOR KEY vk_embedding (embedding) WITH (DISTANCE=COSINE, TYPE=HNSW)
) DEFAULT CHARSET = utf8mb4;
```

`char_start`、`char_end` 与 `start_line`、`end_line` 在入库时一次算好，检索时直接返回，避免「结果有了、出处还要再找一遍」。

## 检索流程

1. 术语扩展：查 `zx_aliases`，把「召回率」扩成「召回率 recall」，把「HNSW」扩成「HNSW 向量索引 近似最近邻」。
2. 全文检索：`MATCH(body) AGAINST(? IN NATURAL LANGUAGE MODE)`，取前 40 条。
3. 向量检索：`ORDER BY cosine_distance(embedding, ?) APPROXIMATE LIMIT 40`，走 HNSW 索引；相似度低于阈值或明显低于最佳结果的候选丢弃。
4. RRF 融合：`score = Σ 1/(60 + rank)`，同一片段被两条通道同时命中时分数叠加，输出时标明 `fts`、`vector` 命中通道。
5. 组装证据包：按预算逐条装入，记录实际字节数与引用信息。

## 为什么向量维度是 384

本地哈希向量化不需要神经网络：字符二元组 + 英文词元哈希到 384 维，配合次线性词频和 L2 归一化，就能在中英文混排资料上给出稳定的近似相似度。384 维在 HNSW 上的建图与查询成本都很低，百级、万级片段都不需要调参。它的边界也很清楚：**同义改写只能靠术语表兜底，真正的语义泛化要换成外部 embedding 模型**，这一点在文档里写清楚，不夸大。

## 取舍记录

- 没有把原文切碎成句子级：句子太短，证据包容量利用率低；按小节 + 500 字左右切块，引用仍然精确到字符区间。
- 没有引入消息队列或后台任务：导入是同步的，百篇规模秒级完成，复杂度不值得。
- 没有把向量写进独立表：同一行同时有正文、向量和引用坐标，避免了检索后回表拼接。
