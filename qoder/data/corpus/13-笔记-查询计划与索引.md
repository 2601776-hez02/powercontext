# 数据库笔记：查询计划与向量索引的选择

## 为什么要看查询计划

「我建了向量索引，为什么还是慢？」——因为优化器可能根本没用它。看 `EXPLAIN` 是最直接的验证：

```sql
EXPLAIN SELECT id, cosine_distance(embedding, :q) AS d
FROM zx_chunks
ORDER BY cosine_distance(embedding, :q) APPROXIMATE
LIMIT 6;
```

计划里如果出现 `VECTOR INDEX SCAN`，说明走了 HNSW；如果只有 `TABLE FULL SCAN` + `TOP-N SORT`，就是全表算距离再排序。

## 常见原因

1. **漏写 `APPROXIMATE`**：没有它，优化器按普通表达式排序处理，通常选择全表扫描。
2. **WHERE 条件过多**：过滤列没有合适索引时，优化器可能放弃 ANN 扫描，改为先过滤再算距离。
3. **数据量太小**：几十行数据下全表扫描代价更低，优化器选全扫是合理的，不代表索引没用。
4. **距离函数与索引定义不一致**：索引是 `COSINE`，查询用 `l2_distance`，可能无法命中索引。

## 我们库里的实践

- 片段表同时有主键、`(document_id, seq)` 普通索引、`ft_body` 全文索引、`vk_embedding` 向量索引。
- 检索只做「向量排序 + LIMIT」，过滤和去重放在应用层，避免干扰索引选择。
- 站点上展示的查询计划来自真实 `EXPLAIN`，不是手写截图。

## 全文索引这边

`MATCH(body) AGAINST(? IN NATURAL LANGUAGE MODE)` 走全文索引；如果查询串全是停用词或被分词器丢掉，会返回空集，此时需要兜底成 `LIKE` 子串匹配——这属于产品行为，不属于数据库问题。

## 排障清单

1. `SHOW INDEX FROM zx_chunks` 确认索引存在且类型正确。
2. `EXPLAIN` 看算子。
3. 用 `EXPLAIN` 里同一段 SQL 直接在客户端跑，排除应用层拼装问题。
4. 数据量小的时候，人工对比「走索引」和「全扫」的结果是否一致，确认召回没有因为近似而下降。
