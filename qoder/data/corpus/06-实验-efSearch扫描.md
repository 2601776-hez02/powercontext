# 实验记录：efSearch 扫描（召回率与延迟）

## 目的

验证 HNSW 的 `efSearch` 对召回率和查询延迟的影响，给出资料库规模下的推荐值。

## 设置

- 语料：16 篇 Markdown，约 90 个片段，384 维本地哈希向量。
- 距离：余弦距离，HNSW，`M=16`，`efConstruction=200`。
- 查询：12 条人工构造的问题，覆盖参数名、中文术语、中英混写三类。
- 指标：Top5 命中率（人工判断是否相关）、单次检索耗时中位数（毫秒）。

## 结果

| efSearch | Top5 命中率 | 延迟中位数 |
| --- | --- | --- |
| 32 | 0.72 | 7.8 ms |
| 64 | 0.83 | 9.1 ms |
| 128 | 0.87 | 13.4 ms |
| 200 | 0.88 | 19.6 ms |

## 结论

- 从 32 到 64 召回提升明显（+11 个百分点），延迟只多 1.3 ms，**64 是甜点**。
- 128 之后收益快速衰减，200 与 128 基本持平但延迟接近翻倍。
- 召回的主要瓶颈不在 `efSearch`：同一批查询里，失败的 3 条都是因为「分块把结论切到了下一块」或「术语没有扩展」，不是图搜索没找到。

## 后续动作

1. 先做分块大小实验（见「分块大小对比」），确认 500 字是否合适。
2. 给高频术语补别名（recall / 召回、latency / 延迟、ANN / 近似最近邻）。
3. 数据量过万后重跑本实验，观察 `M=16` 是否仍够用。

## 备注

本实验只测了延迟，没有测内存；HNSW 的内存占用主要跟 M 和向量维度有关，384 维、M=16 的情况下每千条片段约几 MB，暂时不是瓶颈。
