# 选型：为什么用嵌入式 seekdb 而不是再起一个服务

## 候选

1. **SQLite + FTS5**：轻，但向量检索要额外扩展，中文分词也要自己接；跨平台 wheel 不统一。
2. **PostgreSQL + pgvector**：能力全，但要单独部署、维护连接和账号，对「个人本机工作台」太重。
3. **嵌入式 seekdb**：一个 Python 包拉起完整实例，SQL 兼容 MySQL，自带 `VECTOR` 类型、HNSW 向量索引和 `FULLTEXT ... WITH PARSER ngram` 全文索引，正好覆盖「全文 + 向量 + 事务」三件事。

## 选择嵌入式 seekdb 的理由

- **零外部服务**：`pip install pylibseekdb` 之后 `open(path)` 就能用，不需要 Docker、不需要账号体系。
- **一套 SQL 解决两类索引**：片段表上同时建 ngram 全文索引和 HNSW 向量索引，检索用两条 SQL，融合在应用层做，逻辑清晰。
- **事务**：导入一篇资料时「删旧片段 + 插新片段 + 更新文档」在一个事务里，失败自动回滚，不会留下半篇资料。
- **跨平台**：PyPI 提供 Linux / macOS / Windows 轮子，Windows 上也能本地开发和演示。

## 代价

- **单进程**：嵌入式实例独占数据目录，不能像独立数据库那样多进程并发写。对个人工作台是可接受的，团队协作场景要换成服务端部署。
- **生态较新**：某些 SQL 语法（窗口函数、`FIELD()` 等）支持情况要以实测为准，代码里尽量用标准写法。
- **数据在本地**：换机器要拷贝目录，没有云端同步。

## 结论

「个人 / 小团队的本地学研工作台」这个场景，**部署成本**比**极限并发**重要得多。嵌入式 seekdb 让「下载代码 → 装依赖 → 一条命令初始化」成为可能，这是选它的决定性理由。

如果将来要做多人协作，把同一套表结构迁到 OceanBase 服务端即可，检索 SQL 不用改。
