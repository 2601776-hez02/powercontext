## 1. 模型与量化

**模型**：`bge-small-zh-v1.5`（BAAI，MIT），ONNX 版本取自 `Xenova/bge-small-zh-v1.5` revision `75c43b0`，512 维、中文优化，可直接在浏览器里跑。`npm run fetch-models` 按固定 revision 从 HF 镜像拉取并写入 `SOURCE.json`。

**量化方案**：同一套权重的三种精度，通过 Transformers.js 的 `dtype` 切换对应文件，模型结构不变。

| 精度 | 文件 | ONNX 权重 | 含 tokenizer 的总体积 | 相对 FP32 |
| --- | --- | ---: | ---: | ---: |
| FP32 | `onnx/model.onnx` | 90.46 MB | 90.98 MB | 1.00× |
| FP16 | `onnx/model_fp16.onnx` | 45.30 MB | 45.82 MB | 1.99× |
| INT8 | `onnx/model_quantized.onnx` | 22.90 MB | 23.42 MB | **3.88×**（权重口径 3.95×） |

INT8 是动态量化（权重 int8、激活按 batch 动态 scale），使用官方发布的 `model_quantized.onnx`；FP16 为权重半精度转换，只在 WebGPU 上启用（WASM 无 fp16 算子）。

**检索质量变化**（32 条查询、同一批向量、同一套索引，混合检索口径）：

| 配置 | Recall@5 | Hit@1 | MRR |
| --- | ---: | ---: | ---: |
| FP32 + WebGPU | 0.938 | 0.781 | 0.845 |
| FP16 + WebGPU | 0.938 | 0.781 | 0.845 |
| INT8 + WASM | 0.938 | 0.750 | 0.825 |
| FP32 + WASM | 0.938 | 0.781 | 0.845 |

结论：Recall@5 四档完全一致，Hit@1/MRR 的 0.03 差距小于查询间离散度（12 条改写类里本身有 2 条没进前五）。用 1/3.88 的体积换几乎相同的检索质量，是本题最划算的优化。

## 2. 端侧运行：WebGPU 优先 + WASM 自动降级

- 运行时：Transformers.js 4.3.2（内含 ONNX Runtime Web 1.31.0-dev.20260911）。JS/WASM 产物全部放在 `web/vendor/`，配合 `env.allowRemoteModels=false`、`env.localModelPath='/models/'`、`env.backends.onnx.wasm.wasmPaths` 指向本地文件——**没有任何 CDN 依赖**，断网可导入可检索。（注：WebGPU 用的是 ORT 的 asyncify 胶水，jsep 那支是纯 CPU SIMD 构建，选错会报 `webgpuInit is not a function`，已在本仓库固化。）
- 推理跑在 Web Worker（`web/embed-worker.js`），主线程只做 UI，长文导入不卡页面；批内按文本长度排序后再分批（长度分桶），减少 padding 浪费。
- **WebGPU 选择**：先 `navigator.gpu.requestAdapter({powerPreference:'high-performance'})` 探测，拿到适配器才用 `device:'webgpu'` + `dtype:'fp16'` 初始化。
- **自动降级**：探测失败或 `pipeline()` 抛错时，自动用 `device:'wasm'` + `dtype:'int8'` 重建，把 `fallbackFrom` 回传界面；顶部状态条显示「后端：WASM」，卡片下方给出提示「请求 WebGPU 不可用，已自动降级到 WASM」。
- **降级路径已验证**：`?nogpu=1` 模拟无 WebGPU 环境，实测 `fallbackFrom=webgpu`、实际后端 `wasm`，导入/写入/混合检索全流程正常（`bench/results/fallback-no-webgpu.json`）。

实测（26 个片段，批 8）：

| 配置 | 加载 | 预热 | 向量化 | 吞吐 |
| --- | ---: | ---: | ---: | ---: |
| WebGPU + FP16 | 2933 ms | 270 ms | 435 ms | **59.8 块/s** |
| WebGPU + FP32 | 3280 ms | 297 ms | 530 ms | 49.1 块/s |
| WASM + INT8 | 2608 ms | 183 ms | 5005 ms | 5.2 块/s |
| WASM + FP32 | 2817 ms | 154 ms | 8361 ms | 3.1 块/s |

WebGPU 的向量化吞吐约为 WASM 的 **11.5 倍**（59.8 vs 5.2 块/s），这是"优先 WebGPU"最直接的理由。代价是加载多 0.3–0.5 s（GPU 管线编译），已计入加载/预热，不混入检索延迟。

## 3. seekdb 使用：表结构、混合检索、增量与刷新

**表结构**（seekdb-js `createCollection` 生成，集合名 `kb_chunks`）：

```sql
CREATE TABLE `c$v2$<collectionId>` (
  `_id` varbinary(512) NOT NULL,
  `document` string DEFAULT NULL,
  `embedding` VECTOR(512) DEFAULT NULL,
  `metadata` json DEFAULT NULL,
  PRIMARY KEY (`_id`),
  FULLTEXT INDEX `...` (`document`) WITH PARSER ngram (ngram_token_size = 2),
  VECTOR INDEX `...` (`embedding`) WITH (type = hnsw, distance = cosine, m = 16, ef_construction = 200)
);
```

正文、向量、元数据（`docId/title/source/chunkIndex/chars`）同表同 id；写入用 `upsert`，同一片段重复导入是覆盖而不是主键冲突，因此"重新导入整篇文档"幂等。

**混合检索在库里完成**：`collection.hybridSearch()` 在 seekdb 内部调 `DBMS_HYBRID_SEARCH`——先 `SET @search_parm = '{全文查询, knn, rank.rrf, size}'`，再由 `DBMS_HYBRID_SEARCH.GET_SQL()` 生成**一条** SQL 执行。生成物是一个 FULL JOIN：左侧 `match(document) against(...)` 取全文候选（LIMIT 800），右侧 `cosine_distance(...)` 取向量的 40 条候选，最后的 `_score` 就是 `1/(keyword_rank+60) + 1/(semantic_rank+60)`。界面「seekdb 实际执行的 SQL」面板直接展示这条语句与三条语句的逐条耗时（512 维向量以字面量内联，整条 SQL 约 23.8 KB），可据此确认客户端没有分两路取数再合并。纯向量（`ORDER BY cosine_distance(...) APPROXIMATE`）与纯全文（`MATCH ... AGAINST` + 相关度排序）同样各是一条 SQL。

**增量写入与索引刷新**：导入按 64 条一批 `upsert`；刷新由界面开关控制，默认"导入后刷新一次"，即 `collection.refresh_index()` → `CALL dbms_index_manager.refresh()`（26–55 片段实测 0.30–0.41 s）。不做"每条写入都刷新"——那会把一次 26 条导入从 1.2 s 拖到 20 s 以上。

**可见性验证**：在已有 26 个片段后追加 2 篇新文档（+29 片段），刷新后用只出现在新文档里的事实提问（"EdgeKB 服务默认监听哪个端口，怎么清空知识库"），前 5 条命中 `edgekb-runbook`；8 档配置各测一次，8/8 命中。增量导入本身：向量化 87 ms（WebGPU）/ 652 ms（WASM），写入 161 / 143 ms，刷新 0.30–0.40 s。

## 4. 状态管理与优化项

- **集合状态**：集合元数据由 seekdb 的 `sdk_collections` 表维护；`POST /api/reset` 删除集合并用同一 schema 重建，避免"删表重建后索引配置漂移"。
- **会话状态**：前端 `state`（后端/精度/批大小/知识库统计/最近一次指标）与 `/api/status` 同步；重置或增量导入后片段数立即刷新。
- **已做的优化与实测**（同机同语料，全表见 `docs/measurements.md`）：

| 优化项 | 做法 | 效果 |
| --- | --- | --- |
| 量化 | INT8 / FP16 | 90.98 → 23.42 / 45.82 MB（3.88× / 1.99×），Recall@5 不变 |
| 本地静态资源 | 模型与 ORT wasm 全部本地 | 无 CDN 往返、断网可用；加载 2.3–3.3 s（含 23–91 MB 读盘与 session 创建） |
| 预热分离 | 首次推理单列 `warmupMs` | 冷启动不污染检索延迟（GPU 270 ms / WASM 154–200 ms） |
| 批处理 | 导入批 8、交互批 1 | WebGPU 批 8 比批 1 快 2.2×（435 vs 960 ms） |
| 长度分桶 | 批内按文本长度排序再分批 | WASM 批 8 从 6.8 s 降到 5.0 s（26 片段） |
| 索引刷新策略 | 导入后刷新一次 | 26 条导入 1.2 s + 0.30 s 刷新；逐条刷新不可接受 |
| 检索只取需要字段 | `include:['documents','metadatas','distances']` | 混合检索库内 23–26 ms，端到端 47–64 ms |
| WASM 线程 | `numThreads` 自动（本机解析为 4） | 强制 1 线程时同一批 26 片段要 18.7 s（慢 3.7×） |

**一个反直觉的实测结论**：WASM 后端上"批越大越快"不成立。批 1 向量化 26 个片段 4.4 s，批 8 为 5.0 s，批 16 约 6.0 s；把线程从 4 降到 1 直接掉到 18.7 s，说明多线程本身有效，问题不在线程。合理推断是 WASM 上每批要做更大的内存分配与 padding，短文本被同批长文本拉长后总算力反而增加——这与 WebGPU 上批 8 比批 1 快 2.2× 正好相反。因此产品策略是：**WebGPU 批量导入用批 8，WASM 保持小批**；界面上的批大小开关默认 8 但可改成 1。

## 5. 结论与限制

- 端侧方案成立：文档与查询向量化都在浏览器里完成，服务端只存不算；INT8 后模型 23 MB、断网可用，检索质量与 FP32 持平。
- 检索确实发生在 seekdb：混合检索是一条由 `DBMS_HYBRID_SEARCH` 生成的 SQL，全文候选、向量候选与 RRF 融合都在库内完成，界面可逐条查看语句与耗时。
- 主要限制：嵌入式 seekdb 单进程独占数据目录；评测集只有 32 条查询，指标用于横向对比而非通用质量结论；WASM 批量吞吐受 padding 与内存影响，需要按后端选择批大小。
