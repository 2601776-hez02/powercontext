# 性能优化：批处理、预热与索引刷新策略

端侧知识库的耗时可以拆成五段，各段的优化手段完全不同。

**模型加载**：体积决定首屏。INT8 把 90 MB 压到 23 MB；再把模型与 ORT 的 WASM 从 CDN 换成本地静态文件，省掉 DNS 与跨域往返。页面可以先用 `fetch` 预热模型文件，让真实的 `pipeline()` 调用只做反序列化与会话创建。

**推理延迟**：单条推理的固定开销（kernel 启动、张量拷贝）在大 batch 下会被摊薄。批大小从 1 提到 8，吞吐通常能翻倍；再往上收益递减，而且会拉高单次延迟与内存占用。交互式查询保持 batch=1，批量导入用 batch=8 到 16。

**写入与索引刷新**：批量写入比逐条写入快一个数量级；但 `CALL dbms_index_manager.refresh()` 是一次全局刷新，在只有几十条片段时也要接近 2 秒。策略是“导入结束刷新一次”，不要在每次写入后刷新；交互式场景可以只在新数据必须立即可见时才刷新。

**检索延迟**：HNSW 的查询代价主要取决于 `ef_search` 与候选窗口；混合检索还要叠加全文与 RRF 的开销，但仍在毫秒级。真正拖慢检索的是把整段正文一起返回，所以只 `include` 需要的字段。

**端到端**：用户点下搜索到看到结果 = 查询向量化 + 网络往返 + 数据库检索 + 渲染。优化时要分段计时，不能只报一个总数。
