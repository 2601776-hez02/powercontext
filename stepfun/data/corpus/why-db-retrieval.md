# 为什么检索必须留给数据库

把向量放进 IndexedDB、在 JavaScript 里遍历算余弦相似度，是最容易写出来的“本地知识库”。它在几十条片段时看起来完全够用，但很快就会撞上三堵墙：

1. **复杂度**：暴力检索是 O(N·d)，1000 条 512 维向量就是 50 万次乘加，几百毫秒起步；上万条时直接不可用。
2. **混合检索**：全文检索需要倒排索引与相关度打分，光靠 `String.includes` 既没有分词也没有排序，语义检索与词面检索无法统一排序。
3. **一致性**：增量导入、删改、去重、元数据过滤都要在应用层自己实现，一旦数据量上来就会出现“界面上有、检索不到”的错位。

正确的分工是：浏览器只做它擅长的事（分词前的处理、模型推理、把向量和正文提交给后端），检索交给数据库。seekdb 同时具备向量索引与全文索引，并且能把两路候选放进同一条 SQL 做 RRF 融合，这意味着“混合检索”不是一个应用层算法，而是数据库的一个查询计划。

判断标准很简单：如果关掉应用层代码，只用数据库客户端执行一条 SQL 就能得到同样的排序结果，那么检索确实在数据库里；如果必须先把两路结果取回应用再合并，那就只是“用了数据库存数据”，不是“用数据库检索”。
